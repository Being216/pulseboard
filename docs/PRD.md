# Being任务管理器Web版 — PRD v0.2（终稿）

> 2026-09-08 定稿。基于人类初稿扩展，决策点已拍板：冲突处理=方案A，汇报触发=状态变化+提醒按钮。

## 1. 产品定位

把 being 在后台运行的所有任务状态展示出来，同时有提醒 being 跟进的能力。

这是人类与 being 的**共享工作台**——人类看得到、改得动，being 同步得了、汇报得上。

## 2. 任务数据模型

每个任务的标准字段：

- `id` / `title` / `status`（三态之一）/ `summary`
- `milestones[]`：里程碑列表，各自 `done` + `note`
- `next`：下一步动作（一句话，人类一眼知道卡在哪）
- `blocked_on`：卡点（如「等人类拍板」「等飞书配置」）
- `updated_at` / `last_heartbeat_at`

## 3. 任务生命周期（状态机）

```
想法设计中 → 任务进行中 → 历史任务（完成）
                ↘ 取消（归入历史，标 cancelled）
```

- 想法 → 进行中：being 或人类任一方启动
- 进行中 → 历史：里程碑全 done，或人类手动归档
- 「刷新」= being 重新同步该任务状态并汇报回飞书

## 4. 三栏交互

- 同类型任务同条目、可展开折叠
- 折叠态显示 `title + next + 卡点标记`；展开态显示里程碑进度条
- 任务卡片上有「提醒 being」按钮 → 发提醒到飞书

## 5. 任务操作语义

- **可管理**：改 title / summary / next
- **可取消**：移入历史，being 收到后停止跟进
- **可修改内容**：人类直接在页面编辑 → 写回 tasks.json → being 下个心跳读到
- **可刷新**：触发 being 立即同步该任务（不等下个心跳）

## 6. 同步机制

- being 每心跳写 `tasks.json`
- 页面每 30s 自动拉 `/api/tasks`
- 页面写操作 POST `/api/tasks/:id` → server 落盘 → being 心跳感知

## 7. 写入权与冲突处理【已拍板：方案 A】

**being 写为主，人类写优先**：人类编辑后加 `human_edited` 标记，being 心跳不覆盖该字段，直到 being 主动确认吸收。

语义简单：人类永远赢，being 负责吸收。

## 8. 提醒与汇报触发条件【已拍板：① + ③】

- ① 任务状态变化时 → being 推送飞书
- ③ 人类点「提醒 being」按钮时 → being 收到后跟进并回复

（②里程碑完成不触发——太吵；④每日简报可后续版本再加。）

## 9. 非功能

- 本地 server（127.0.0.1:8765）→ 后续迁 pulseboard 部署
- 无登录（家用内网），公开仓库只放代码不放数据

## 10. 里程碑规划

- v0.1 ✅ 本地看板（server + 页面 + tasks.json）
- v0.2：任务操作全语义（取消/修改/刷新）+ 写入冲突处理（human_edited 标记）
- v0.3：提醒按钮 → 飞书双向
- v1.0：pulseboard 正式部署
